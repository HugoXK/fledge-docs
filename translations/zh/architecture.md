# 架构

## 原则

- **审批有范围**：Fledge 的审批只授权 Fledge 本身，不签发其他产品的权限或会话。
- **由人合并**：每个任务只创建一个聚焦的 PR；不推送默认分支、不强推、不合并。
- **平台不是代码运行器**：平台编排 FlyBot agent，agent 在自己的工作区执行；Fledge 不执行用户仓库。
- **每仓库隔离**：容器、数据卷、网络、模型代理与凭据按仓库隔离。

## 组件

| 组件 | 职责 |
| --- | --- |
| Web 控制台 | 用户、仓库、任务、计划、审查、设置与审计 |
| 任务队列 | 持久队列、租约、心跳、超时与恢复 |
| FlyBot bridge | 把任务交给隔离的 FlyBot 实例，并回收结果 |
| 模型代理 | 按用户/任务注入 `flg_` token，计量平台额度 |
| GitHub 集成 | OAuth、仓库 token、PR、检查与合并状态 |
| 审计与账本 | 任务、成本、审批、token 与操作记录 |

## 任务生命周期

```
创建任务 → 计划 → 人工批准 → 隔离环境执行
        → 失败测试 → 修复 → 项目检查 → PR
        → 人工审查 → 合并（或关闭）
```

计划在开始前可见；高风险操作需要批准。任务失败会记录原因、重试次数与是否需要人工处理；运行中的任务有超时与无心跳停滞检测。

## 信任边界

- GitHub token、用户模型 Key、SMTP 凭据与会话密钥只在控制面加密保存。
- 每个仓库的容器使用独立 bridge token 与模型代理；不能使用操作者的模型 Key。
- 用户提交的 URL、分支名、仓库名与回调内容都按不可信输入校验。
- 合并权始终属于仓库维护者；Fledge 不合并自己的 PR。

## 数据

核心表包括用户、仓库、任务、计划、运行、token、审批、配额账本与审计。SQLite 使用 WAL 与外键；迁移在启动时执行。详细数据模型见英文参考 [data model](/docs/architecture/)。
